## 要点（結論）
- ✅ `.test` は RFC で**テスト用に予約**されており、ルートに委任されない。ローカルで自由にゾーンを作って構築してOK。
- ✅ ローカルで `host.black-ghost.test` を A/AAAA/CNAME 等で作れば、そのDNSを参照する端末からは解決する。
- ✅ 外部（Google DNS / ISP DNS / 公開インターネット）は名前解決しない＝事故で外に届く心配が小さい。

---

## 実務上の注意点（要チェック）
1. **DNSサーバの権限を明確に**  
   - ローカルの名前解決専用サーバ（dnsmasq, BIND, CoreDNS, systemd-resolved の stub）でゾーンを“権威的”に持たせる。フォワーダーを使う場合はそのゾーンをフォワードしないように設定。

2. **クライアントのDNS設定**  
   - クライアントが必ずローカルDNSを参照するように（DHCPでDNS配布、または /etc/resolv.conf / network manager 設定）。公衆ネットワークやVPN接続で外部DNSにフォールバックすると解決されない・衝突することがある。

3. **検索ドメインとFQDN**  
   - `server` のように短い名前を打つと検索ドメインが自動で付与され、望まない解決が起きることがある。問題を避けるには FQDN（末尾に `.` をつける）を使う習慣をつけるか、検索ドメイン設定を整備する。

4. **証明書（TLS）は公的CAで取れない）**  
   - Public CA は `.test` に対して証明書を発行しない（大手は発行不可）。HTTPSで本当に「信頼された」接続を作りたいなら、社内CAまたは mkcert / dev CA を使う必要あり。自己署名だとブラウザ警告が出る。

5. **メールは外に出ない（利点／欠点）**  
   - `user@black-ghost.test` 宛のメールはパブリックに配送されない（良い）。ただしローカルでSMTP配信テストする場合、配送失敗やクライアントの挙動に注意。

6. **他のネットワークとの衝突（VPN/会社ネットワーク）**  
   - VPN接続先のDNSポリシー（split-DNS）や社内の別ゾーンとぶつかる可能性がある。全社で同じ運用方針にするか、名前空間を工夫する（例：`dev.test` vs `lab.test`）こと。

7. **`.local` と混同しないこと**  
   - `.local` は mDNS 用で別問題。`.test` は普通の DNS ゾーンとして扱われるので、衝突や意図しないマルチキャスト挙動が少ない（ただし両方使うと複雑化する）。

## 実例：簡単な設定スニペット

### dnsmasq（簡単・軽量）
`/etc/dnsmasq.d/black-ghost.conf`
```

address=/black-ghost.test/192.168.1.10

```
再起動して、クライアントの DNS を dnsmasq に向ければ解決します。

### BIND（権威サーバでゾーンを管理する場合）
`named.conf.local`
```

  type master;
  file "/etc/bind/zones/db.black-ghost.test";
};
```
`/etc/bind/zones/db.black-ghost.test` は典型的なゾーンファイルを書く（SOA/NS/A 等）。

### systemd-resolved（ローカル単一ホスト向け）
`/etc/hosts` に書いても良い：簡単なテストならこれで手早く解決可能。

## TLS 用の実用的オプション
- **mkcert**：開発用にローカルCAを作り、ブラウザで信頼される証明書を自動発行できる。超便利。
- **社内CA（Vault/step-ca/ADCA）**：運用向け。端末にCA証明書を配布して信頼させる。
- **自己署名**：簡単だがブラウザ警告が出る。テストサーバ限定なら可。

## 運用ポリシー提案（社内用）
